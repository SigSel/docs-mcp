# Measurements

The numbers behind the README, with how they were taken, so they can be
rerun and compared over time. Rerun after changes to search, the images or the
SDKs, and update this file in the same commit.

## Search quality across languages

**Question.** Users ask in Nynorsk, Bokmål or English. How often does search put
the right page first, and in the top 3?

**Method.** `conformance/search_eval.json` holds 36 questions about an
internal developer handbook (55 pages, written in Nynorsk). Each question
names its right page or section and is written four ways:

| Variant | Example (`dep-vulnerabilities`) |
|---|---|
| `nn`: Nynorsk | `sårbarheiter i avhengigheiter` |
| `nb`: Bokmål | `sårbarheter i avhengigheter` |
| `en`: English, word for word | `vulnerabilities in dependencies` |
| `assistant`: what a model writes when the server says the docs are in Nynorsk: Nynorsk keywords plus Bokmål and English variants | `sårbarheiter sårbarheter vulnerabilities avhengigheiter avhengigheter dependencies` |

I wrote the `assistant` queries by hand, as a stand-in for what a model
produces from the English question after reading the server's instructions.
They were not generated by a live model.

A question counts as found at rank *n* when the *n*-th result's `path`, or
`path#anchor`, is one of its targets.

The questions stay out of the repo, like the handbook they are about. To
measure your own docs, write yours to `conformance/search_eval.json`, which git
ignores:

```json
{"languages": ["nn", "nb", "en", "assistant"],
 "queries": [
  {"id": "rs-203", "targets": ["rust/rules.mdx#rs-203"],
   "nn": "unwrap i produksjon", "nb": "unwrap i produksjon", "en": "unwrap in production",
   "assistant": "unwrap panikk panic produksjon production"}]}
```

`just eval` (or `uv run python search_eval.py <docs> --impl <impl>` in
`conformance/`) reruns it. Every implementation gives identical results.

**Results.** Right page first / in the top 3:

| Search | nn | nb | en | assistant |
|---|---|---|---|---|
| v0.1: BM25 over sections, title, headings, metadata | 78% / 89% | 75% / 89% | 44% / 58% | 61% / 86% |
| + link URLs no longer indexed as words | 78% / 89% | 75% / 89% | 44% / 61% | 75% / 97% |
| + page path indexed (weight 3) | 78% / 89% | 75% / 89% | 67% / 81% | 81% / 94% |
| + one-edit matches for words of 6+ letters (**current**) | **83% / 92%** | **81% / 97%** | **67% / 81%** | **86% / 97%** |

What the steps did:

- **Link URLs.** A see-also list linking to `virtual-environments.mdx` used to
  rank first for "virtual environment", because the file name in the URL was
  indexed as text. Now only the link text is.
- **Page path.** File names describe a page plainly, and in this handbook they
  are English. That is where most of the English gain comes from.
- **One-edit matches.** These bridge Nynorsk and Bokmål spelling
  (`sikkerheit`/`sikkerhet`, `reglar`/`regler`) and typos, without any word
  lists.

Settings near these behave about the same: path weight 2 or 3, one-edit factor
0.3 to 0.5, minimum length 5 or 6. So the result is not a fragile fit to the
36 questions. It is still a small set written by one person, so read it as
direction, not precision.

**Reading it.**

- **Bokmål users are fine.** Most words are shared, and prefix and one-edit
  matching cover much of the rest.
- **English users depend on the assistant** translating the keywords, which the
  server instructions and the tool descriptions ask for. With that, English
  questions land where Nynorsk ones do. A client that ignores the
  instructions and searches in English word for word gets two in three right
  first time.
- **What is left.**
  - The assistant variant's five misses all have the right page at rank 2 to 4.
    In some, the top hit is a fair answer too, such as a section on rebasing for
    "rewrite published history".
  - Word-for-word English misses where no Norwegian word or file name lines up:
    - "quality gates in CI", for a Nynorsk heading that shares no word with it;
    - "add a dependency cargo": `dependency` is two edits from the file name
      `dependencies`.

  Multilingual embeddings would close those, at the cost of hosting a model.

## Container footprint and latency

**Method.** `just image` builds the images; `just measure` (or
`uv run python measure.py <handbook checkout> --dir src/content/docs` in
`conformance/`) then, for each image in turn:

1. Reads the image size from `podman image inspect`.
2. Starts the container with the handbook mounted read-only, and times
   `podman run` until `/readyz` answers `200`. That covers container start,
   process start, reading and indexing all pages.
3. Waits 3 seconds and reads memory from `podman stats`.
4. Over one MCP client session, runs every question in `search_eval.json` in all
   four variants (144 searches) three times, plus three `read_doc` calls for the
   largest page. All calls are sequential, from the same machine.
5. Reads memory again.

**Results.**

The TypeScript implementation was removed on 2026-10-29, after these runs.
Its columns stay as a record.

Measured 2026-10-29 on an 11th Gen Intel Core i7-1185G7 (8 threads), 15 GB
RAM, Fedora 44 (Linux 7.2), podman 5.8.9. The code was commit 56a250f plus
updated dependencies (rmcp 3.8, Starlette 1.10). The docs were the
same handbook (55 pages). Each implementation got 432 searches and 3 reads of
the largest page (30 kB).

| | Rust | Python | TypeScript |
|---|---|---|---|
| Image size | 200 MB | 276 MB | 364 MB |
| `podman run` to ready | 0.48 s | 3.12 s | 0.89 s |
| Memory, idle | 9 MB | 63 MB | 54 MB |
| Memory, after the load | 11 MB | 64 MB | 116 MB |
| search_docs, median | 4.3 ms | 10.9 ms | 10.0 ms |
| search_docs, 95th percentile | 6.3 ms | 20.1 ms | 14.7 ms |
| read_doc (largest page), median | 3.5 ms | 5.8 ms | 8.0 ms |

Latency is measured at the client, so it includes HTTP and JSON-RPC overhead.
It varies by up to about 15% between runs: the same TypeScript image measured
9.2, 12.7 and 6.7 ms for the three latency rows in a run the same afternoon,
at commit 56a250f.

Earlier run, 2026-10-15, same machine on Fedora 42 (Linux 6.19), podman 5.8.2.
The code was the language changes on top of commit 9934999, before `tini`:

| | Rust | Python | TypeScript |
|---|---|---|---|
| Image size | 200 MB | 275 MB | 363 MB |
| `podman run` to ready | 0.49 s | 3.12 s | 0.92 s |
| Memory, idle | 10 MB | 67 MB | 55 MB |
| Memory, after the load | 11 MB | 67 MB | 115 MB |
| search_docs, median | 4.1 ms | 10.5 ms | 9.5 ms |
| search_docs, 95th percentile | 5.9 ms | 19.5 ms | 13.2 ms |
| read_doc (largest page), median | 3.2 ms | 5.4 ms | 7.1 ms |

Earliest run, at commit 9934999 (before the language changes), measured by hand
with the same method minus latency:

| | Rust | Python | TypeScript |
|---|---|---|---|
| Image size | 199 MB | 275 MB | 363 MB |
| `podman run` to ready | 0.65 s | 3.22 s | 0.95 s |
| Memory, idle | 9 MB | 66 MB | 54 MB |

**Reading it.**

- Most of every image is `git` and its dependencies, which every implementation needs
  for syncing. The Rust binary itself is a few MB.
- Every implementation answers in a few milliseconds, which is negligible next
  to the model calling it. Startup only matters for how quickly a new pod
  becomes ready.
- Memory is where they differ most. TypeScript grew under load until V8
  collected garbage. Even that was well inside `deploy/k8s/base`'s 256 MiB
  limit (it requests 64 MiB).

## Consistency between implementations

**Method.** `just compare` (`compare.py`) starts every implementation
against the same docs tree and diffs everything they return:

- `docs_overview` and `list_docs`;
- `read_doc` for every page;
- `read_doc` and `get_section` for every section anchor;
- `search_docs` for the eval questions plus words sampled from the pages.

Scores may differ by at most 0.002; everything else must be identical.

**Results.**

Run 2026-10-15, after the language changes:

| Docs tree | Pages | Section reads | Searches | Comparisons | Differences |
|---|---|---|---|---|---|
| The handbook (Starlight, `.md`/`.mdx`) | 55 | 806 | 136 | 2008 | 0 |
| The handbook as a VitePress site (`.md`, nn + root language) | 97 | 1595 | 136 | 3670 | 0 |
| The handbook as a Zensical site (`.md`, `en/` + `nn/`) | 96 | 1594 | 136 | 3666 | 0 |

The conformance suite (`just test`) adds 138 checks per implementation against
`fixtures/docs`, including byte-for-byte golden outputs.
